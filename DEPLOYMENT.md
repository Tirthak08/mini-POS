# Deploying Mini-POS

Two things get deployed, in this order:

1. **The backend API** → Render (free tier, Singapore region). MongoDB stays on
   Atlas — nothing moves there.
2. **The Android app** → an `.apk` built by EAS Build, shared directly with
   shopkeepers (WhatsApp / a link). No Play Store account needed for this.

The order matters: the APK bakes in the backend's URL, so the backend must be
live first.

Everything referenced below is already in the repo: `render.yaml` at the root,
`eas.json` and the updated `app.json` in `mobile/`, `.env.example` in
`backend/`. The backend has been boot-tested in production mode
(`NODE_ENV=production`, `npm start`): health returns 200, a full
register → category → product → sale flow works, and the login rate limiter
enforces (11th bad PIN → 429).

## Part 1 — push the repo to GitHub

From `D:\NEW PRO\mini-pos`:

```powershell
git init
git add .
git commit -m "Mini-POS: backend + mobile"
```

Create an empty **private** repo on GitHub (say `mini-pos`), then:

```powershell
git remote add origin https://github.com/YOUR-USERNAME/mini-pos.git
git branch -M main
git push -u origin main
```

Before pushing, confirm no secrets are staged: `git status` must NOT list
`backend/.env`. The root `.gitignore` excludes it; `backend/.env.example` (the
template with no real values) is what gets committed.

### Troubleshooting the push

**Render says "Blueprint file render.yaml not found on main branch."**
The repo was initialised one level too high (at `D:\NEW PRO` instead of
`D:\NEW PRO\mini-pos`), so on GitHub everything sits under `mini-pos/…` and
the root has no render.yaml. Fix by re-rooting:

```powershell
cd "D:\NEW PRO"
Remove-Item -Recurse -Force .git
cd mini-pos
git init
git add .
git commit -m "re-rooted at mini-pos"
git branch -M main
git remote add origin https://github.com/YOUR-USERNAME/mini-pos.git
git push -u origin main --force
```

**`mobile/` shows on GitHub as a greyed-out folder with no files.**
`create-expo-app` ran `git init` inside `mobile/`, and a nested `.git` makes the
outer repo record the folder as an empty submodule pointer instead of pushing
its files. Fix: `Remove-Item -Recurse -Force mobile\.git` (from `mini-pos\`),
then `git add mobile` and commit — the sources push as normal files.

After any of these, verify on github.com that you can browse
`mobile/src/screens/PosScreen.js` and see `render.yaml` at the repo root.

## Part 2 — deploy the backend to Render

1. On render.com: **New + → Blueprint**, connect the GitHub repo. Render reads
   `render.yaml` and proposes one service: `mini-pos-api` (Node, Singapore,
   free plan, health-checked on `/api/health`).

2. It will prompt for the three secrets the blueprint deliberately does not
   contain:
   - `MONGODB_URI` — your Atlas connection string, the same one from
     `backend/.env`. Paste it into the Render dashboard only — never into git,
     chat, or a screenshot.
   - `ADMIN_USERNAME` / `ADMIN_PASSWORD` — pick real values. The server keeps
     admin sign-in **disabled** while the password still contains `replace_me`,
     so a forgotten placeholder fails safe rather than shipping a known password.
   - `JWT_SECRET` is generated by Render automatically (`generateValue: true`).

3. **Atlas network access:** Atlas → Network Access → Add IP →
   `0.0.0.0/0` ("allow from anywhere"). The free Render tier has no fixed
   outbound IP, so an IP allow-list cannot name it. This is acceptable because
   the credentials in the URI are the real lock — but use a strong, unique
   database-user password, and rotate it if it ever leaks. (If you later move
   to a paid Render plan, you can buy a static outbound IP and tighten this.)

4. Deploy. Render marks it live only when `/api/health` returns 200, so a boot
   that cannot reach Atlas fails the deploy instead of the first customer.

5. Note the URL — `https://mini-pos-api-XXXX.onrender.com` — and verify from
   any browser:

   ```
   https://mini-pos-api-XXXX.onrender.com/api/health
   → {"ok":true,"service":"mini-pos-api","mongo":{"state":"connected",...}}
   ```

### The free-tier trade-off, honestly

The free instance **sleeps after 15 minutes idle** and takes ~50 seconds to
wake. For a pilot that is tolerable — the first request of the morning is slow,
then everything is instant. Two ways to remove it:

- Free workaround: an [UptimeRobot](https://uptimerobot.com) monitor pinging
  `/api/health` every 10 minutes keeps it awake. One always-on service fits
  inside the free tier's 750 instance-hours/month.
- Real fix: Render Starter (~$7/mo) — no sleeping. Do this the day a real shop
  depends on the app for its daily takings.

## Part 3 — build the APK

From `D:\NEW PRO\mini-pos\mobile`:

```powershell
npm install -g eas-cli
eas login                      # your expo.dev account
```

Put the real backend URL into `eas.json`: replace both occurrences of
`https://REPLACE-WITH-YOUR-SERVICE.onrender.com/api` with your actual Render
URL — keep the `/api` suffix.

Then:

```powershell
eas build --platform android --profile production-apk
```

First run asks to create an Android keystore — answer **yes, let EAS manage
it**. That keystore signs every future update; EAS storing it means you cannot
lose it with a laptop. The build runs on Expo's servers (~10–15 min) and ends
with a download link to the `.apk`.

That link is what you send to shopkeepers. On the phone: download → open →
allow "install from this source" → install. Sign in with the shop name and PIN.

### Updating the app later

Bump nothing by hand — `autoIncrement: true` manages `versionCode`. Just:

```powershell
eas build --platform android --profile production-apk
```

and share the new link. (Direct-APK installs do not auto-update; shopkeepers
install the new file over the old one. Data is untouched — it lives on the
server.)

### If the APK crashes on launch

The usual cause is a **native module that Expo Go bundles but a standalone build
does not** — the app works perfectly in Expo Go and dies instantly as an APK.
`@expo/vector-icons` needs `expo-font`'s native module, and if `expo-font` is
missing from `package.json`, or installed at a version built for a different
SDK, the first icon render takes the process down. Icons appear on the very
first screen, so it looks like a launch crash.

Always start here:

```powershell
cd "D:\NEW PRO\mini-pos\mobile"
npx -y expo-doctor
```

Two checks matter most. **"Check that required peer dependencies are
installed"** names any native module you are missing — Expo's own warning is
"your app may crash outside of Expo Go without these dependencies." And **"Check
that no duplicate dependencies are installed"** catches two copies of one native
module, which an APK cannot contain.

Install missing modules with `npx expo install <name>` — **never plain
`npm install <name>`**. `expo install` consults the SDK's version map and picks
the matching release; `npm install` fetches *latest*, which for a native module
means code compiled against a different Expo core. That is how you end up with
`expo-font@57` sitting next to the SDK-54 `expo-font@14`.

After changing native dependencies, wipe and reinstall so no stale copy
survives, then confirm one version each:

```powershell
Remove-Item -Recurse -Force node_modules
npm install
npm ls expo-font
```

**If it still crashes,** read the actual reason off the device instead of
guessing. Enable Developer options → USB debugging on the phone, connect it, and
with `adb` (from Android platform-tools):

```powershell
adb logcat -c                                   # clear the buffer
# now launch the app on the phone, let it crash, then:
adb logcat -d *:E > crash.txt
```

Search `crash.txt` for `FATAL EXCEPTION` or `ReactNativeJS` — the lines just
under it name the module. That beats any amount of speculation.

## Part 4 — smoke-test the deployed pair (5 minutes)

On a real phone with the APK, against the Render backend:

1. Register a test shop → you land on the Sell tab.
2. Stock tab → add a category and a product with a photo.
3. Sell → add to cart → discount ₹10 → Complete order → receipt offer appears
   → Share receipt → the PDF opens in the share sheet.
4. Sales tab → the receipt is listed → open it → Share receipt works again.
5. Reports → Today shows the sale.
6. Airplane mode → reopen the app → the catalogue still shows, marked
   "Showing your saved list".
7. Sign out → sign back in with the wrong PIN 10 times → locked out with a
   clear message (the limiter is per-account, so this cannot lock out other
   shops on the same Wi-Fi).

Then delete the test shop from the super-admin screen (sign in with the admin
credentials you set on Render).

## What is deliberately NOT in this setup

- **No Play Store yet.** When the pilot proves out: $25 developer account,
  `eas build --profile production-store` (produces an AAB), plus a store
  listing. Note Google requires new personal accounts to run a closed test
  with 12+ testers for 2 weeks before public release — plan that lead time.
  The `production-store` profile already exists in `eas.json`.
- **No iOS.** ₹8,300/year developer account and the target users are on
  Android. The Expo project builds for iOS unchanged when that day comes.
- **No custom domain.** The `.onrender.com` URL works fine; a domain is
  cosmetic here because users never see the API URL.
- **The web export is a test harness, not a deployment target.** The product
  is the Android app.
